Design Memo: Team Management Tree

Recursive insertion starts at the root and asks one question at each node: is this the manager I am looking for? If it is, the method checks whether the requested side is empty and, if so, attaches a new EmployeeNode there. If it is not, the method calls itself on the left child and then on the right child. Each call handles one node and hands the rest of the search to smaller subtrees, so the tree's shape does the work that nested loops would otherwise have to do.

The main challenge was that the search has to report its result back up the chain of calls. Without a return value, every dead-end branch would look like a failure and "manager not found" would print many times. To fix this, insert() returns True once the manager is found, which also stops the search from checking the right subtree unnecessarily, and only the original top-level call prints the error. A second challenge came from the default current_node=None, because None means "start at the root." Calling insert() on an empty child would restart the search from the top and loop forever, so the method only recurses into children that exist. Taken sides also needed care: a manager with a full side counts as found, so the code reports that the side is taken instead of claiming the manager is missing.

Trees are preferable when data is naturally hierarchical or when searching needs to skip large portions of the data. Organization charts, file systems, and website menus all have parent-child relationships that flat lists represent poorly. Balanced search trees and database indexes also find records much faster than scanning a list, while decision trees model branching choices directly.
